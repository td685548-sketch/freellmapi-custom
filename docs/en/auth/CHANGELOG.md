# Multi-user access domain — Changelog

Doc revision history for `docs/en/auth/`, seeded from the commits that introduced the feature.

## 2026-11-07

- **feat(profiles): end users behind a client key.** A web app calls with one client key for all its visitors; when its backend names the visitor (`X-End-User` header, else the OpenAI `user` field; trimmed, at most 128 printable characters, otherwise ignored), the request row records it (`requests.end_user`, migration `20261107_000002_custom_end_users`). Only client-key traffic is attributed. `GET /api/client-profiles/:id/end-users?days=` lists the key's end users (busiest first, at most 500) with requests, errors, tokens, latency, last request, and how many requests named no end user; `?endUser=` filters the recent requests of the key. **Per-end-user allowance:** `client_profiles.eu_*` (requests / tokens per day / month, NULL = unlimited, `GET|PUT /api/client-profiles/:id/end-user-quota`) is what EVERY end user of the key gets; over it the end user gets `429 end_user_quota_exceeded` with `Retry-After`. It is checked before the key's own allowance, so a refused end user does not touch the key's totals; totals are kept per end user and window in `custom_end_user_counters` (restart-safe, seeded from the request log when first set). Requests that name no end user are bound only by the key's own limits. Dashboard: an **End users** card on the client profile page (allowance editor, search, click a visitor for their requests); the connect examples now send `X-End-User`.

- **feat(usage): recent requests of each client profile and account.** `GET /api/client-profiles/:id/requests` (`view_client_profiles`), `GET /api/admin/users/:id/requests` (`view_users`) and `GET /api/user/requests` (the caller's own) list the newest logged requests of one subject, newest first, paged by id (`?limit=1..100&before=<id>`), with `?status=error` for failures only; `.../requests/:rid/attempts` returns the failover chain behind one of them (404 if the request is not that subject's). Each failed failover attempt is its own row. Dashboard: a **Recent requests** card on the client profile and account usage pages and under "My usage" (expand a row for its attempts, "Load older").
- **feat(usage): usage alerts.** An alert when an account or client key reaches 80% and 100% of a daily or monthly allowance (once per window; the dedup state lives in `settings` as `usage_alert_fired:<kind>:<id>:<window>` and older windows are pruned), and when at least 5 of at least 10 of its requests, and at least half, failed in the last 15 minutes (5xx, or a 429 from the providers; the gateway's own refusals are not counted; at most once an hour per subject, held in memory). Every alert goes to the server log (Logs page, event `usage_alert`) and, when configured, to a webhook (JSON with `type: freellmapi.usage_alert`, the message also in `text` and `content` for Slack / Discord) and to an email address through the configured Gmail sender. `GET|PUT /api/settings/usage-alerts` (`view_settings` / `edit_settings`) and `POST /api/settings/usage-alerts/test`. Dashboard: an **Alerts** card on `/usage` for holders of `view_settings`. Allowance checks run where the allowance is booked and read the database only when a threshold is reached; the error window costs no database access.

- **feat(auth): rotate a client profile's key without downtime.** Upstream's `POST /api/client-profiles/:id/rotate` kills the replaced key at once, so the web app using it breaks until its environment variable is changed. New `POST /api/client-profiles/:id/rotate-with-grace` (`{ graceHours: 1..168 }`, `edit_client_profiles`) issues a new key (returned once) and parks the old one in `custom_profile_previous_keys` (migration `20261107_000001_custom_profile_previous_keys`; SHA-256 only, plus a masked hint) until the grace period ends. Until then the old key authenticates as the same profile: `resolveAuth` and the profile gate fall back to that table only when the current-key lookup misses, so the current key pays nothing; the old key shares the profile's limits, allowances, model list and numbers, and is refused once the profile is disabled or deleted. `GET /api/client-profiles/:id/previous-keys` (`view_client_profiles`) lists the keys still in their grace period (hint and expiry, never the key or its hash); `DELETE` (`edit_client_profiles`) ends every grace period at once. At most five previous keys are kept per profile. Upstream's immediate rotation is unchanged. Dashboard: a **Key rotation** card on the client profile usage page (grace period 1 h / 24 h / 3 days / 7 days, two-click confirm, the new key shown once with a copy button, old keys with their expiry, "End grace period now").

## 2026-11-06

- **feat(auth): "Connect your web app" panel on the client profile page.** A card on `/profiles/:id/usage` with the server address (copyable), copy-paste backend examples in cURL, Node.js and Python (system prompt, page data and chat history shown as entries of `messages`; the key is read from `FREELLM_KEY`, never written into the example) and, for holders of `edit_client_profiles`, a **Send test** button. `POST /api/client-profiles/:id/test` (`{ message?, model? }`) decrypts the profile's key server-side and makes one real `/v1/chat/completions` call with it over the loopback (Host forced to `127.0.0.1:<port>`, so it passes the host allowlist), then returns `{ result: { status, ok, latencyMs, model, platform, reply, usage, error, retryAfter }, profileEnabled }`. Because it is a real call it passes through the key's own gate: model list, token cap, per-minute limit, allowances; it is attributed to the profile (user agent `freellm-dashboard-test`) and counts against them. The key is never returned. The dashboard turns refusals into a one-line hint (model list, rate limit, allowance, rejected key, no enabled allowed model, unknown model).

- **feat(auth): model allowlist and `max_tokens` cap per client profile.** Migration `20261106_000004_custom_profile_restrictions` adds `client_profiles.allowed_models` (JSON list of lowercase model ids) and `max_tokens_cap`; NULL in either means no restriction, so existing profiles are unchanged. `profileInferenceGate` applies them before the per-minute check and the allowances, so a refused request costs the key neither. **Allowlist:** a request naming a model outside the list gets `403 { type: 'permission_error', code: 'model_not_allowed', allowed_models }`. `auto`, `auto:<chain>` or no model is accepted on chat completions, completions, Responses and Messages, where `resolveRoutingChain` now narrows the chain to the allowed models (a clear `400` when none of them is enabled); on every other endpoint (embeddings, images, audio, rerank, Gemini, ...) the key must name an allowed model (`403 model_required`), because their automatic routing is not narrowed. Listings and `count_tokens` pass untouched. **Cap:** a larger `max_tokens` / `max_completion_tokens` (Responses: `max_output_tokens`, Gemini: `generationConfig.maxOutputTokens`) is lowered to the cap, and a request that asks for none gets it. API: `GET|PUT /api/client-profiles/:id/restrictions` (`view_client_profiles` / `edit_client_profiles`; PUT merges); dashboard: a **Restrictions** card on the client profile usage page. Not covered: a pinned model name that the router resolves to equivalent models of other platforms may be served by those; model ids are matched exactly (case-insensitively for the allowlist, but the model lookup downstream is case-sensitive).

- **feat(auth): daily and monthly allowances (requests and tokens) per account and per client profile.** Migration `20261106_000003_custom_usage_quotas` adds `custom_usage_quotas` (the limits; NULL = unlimited, no row = no limit, so existing installs are unchanged) and `custom_usage_counters` (running totals per UTC day `dYYYY-MM-DD` and month `mYYYY-MM`, kept only for subjects that have a limit). Unlike the per-minute window, which lives in process memory and resets on every restart, these totals are in the database and survive restarts and deploys. Both gates (`userInferenceGate`, `profileInferenceGate`) call `enforceUsageQuota` after the per-minute check: a request that finds a window full gets `429 { type: 'insufficient_quota', code: 'user_quota_exceeded' | 'profile_quota_exceeded', period, metric, limit, used, resets_at }` with `Retry-After`. A request is counted when it is admitted (so a parallel burst cannot slip under the limit) and handed back if it fails or the client hangs up; token limits cannot be known up front, so they refuse the NEXT request once the total has reached the limit. Cost: a subject without a limit costs one lookup per 30 seconds and no writes; one with a limit keeps its totals in memory after one read per window and costs one upsert per successful request. Setting a first limit seeds today's and this month's totals from the request log. API: `GET|PUT /api/admin/users/:id/usage-quota` (`view_users` / `edit_user_quotas`, primary admin protected), `GET|PUT /api/client-profiles/:id/usage-quota` (`view_client_profiles` / `edit_client_profiles`), `GET /api/user/usage-quota` (the caller's own, read-only). A PUT merges: fields it names change, the others stay. Dashboard: an **Allowances** card with usage bars on the account usage page, on the client profile usage page and, read-only, under "My usage".

- **feat(auth): usage ranking page and its permissions.** A new permission group `view_usage` ("Usage ranking") with two leaves, `view_usage_accounts` (every account's email and figures) and `view_usage_profiles` (every client profile's name and figures); the parent grants both, a leaf grants only itself, and either appears in the permission editor automatically because it lives in `shared/permissions.ts`. `GET /api/usage/accounts` and `GET /api/usage/profiles` (`?days=1..90`) sit behind the `/api/usage` gate in `PERMISSION_GATES`; `permission-actions.ts` maps each path to its leaf. Each answers every account or profile, idle ones included, with requests, success/error/canceled, tokens, mean and 95th-percentile latency of successes, last request and the per-minute cap. Dashboard: a **Usage** nav entry (shown to anyone holding a `view_usage*` grant) opening `/usage` - one table of both kinds ranked by any column, with a name search, kind switch, hide-idle, only-with-errors and minimum-requests filters, a 7/30/90 day window and a totals row; sort and filters are remembered in the browser. Rows link to the per-account or per-profile page only for viewers who may open it (`view_users` / `view_client_profiles`). No new table or migration: it reads `requests.user_id` / `profile_id`.

- **feat(auth): usage and a request cap per client profile (`sk-cp-…` keys).** Migration `20261106_000002_custom_profile_usage` adds `requests.profile_id` (NULL for every other credential and all earlier rows) and `client_profiles.rpm_limit` (NULL = unlimited). Profiles that already exist stay unlimited; profiles created afterwards default to 60 requests per minute. A new `profileInferenceGate` (mounted beside `userInferenceGate` for `/v1` and `/v1beta`, same credential headers) tags the request with its profile and enforces the cap with `429 profile_rate_limit_exceeded` and `X-RateLimit-*-Profile-RPM` headers; unknown or disabled keys are left to the normal 401. `GET /api/client-profiles/:id/analytics` and `PUT /api/client-profiles/:id/quota` ride on the existing `view_client_profiles` / `edit_client_profiles` permissions; the dashboard gets `/profiles/:id/usage` (the same numbers as per-account analytics plus the limit editor), opened from an icon on each profile row. Upstream's `routes/client-profiles.ts` is untouched.

- **feat(auth): per-account usage analytics.** Migration `20261106_000001_custom_request_user_id` adds a nullable `requests.user_id` (partial index on `(user_id, created_at)`); it stays NULL for the unified key, client profiles, dashboard sessions and all earlier rows, so single-user installs read as before. The `/v1` per-user gate tags the request context (`setRequestUser`), `logRequest` writes `user_id` in the same INSERT (no extra round trip) and tallies successful tokens so `user_monthly_usage.tokens` is finally non-zero. New `GET /api/admin/users/:id/analytics` (`view_users`) and `GET /api/user/analytics`, a `/users/:id/analytics` dashboard page and a **Usage** button on the Users rows, plus a "My usage" section on the member keys view. [02](02-user-api-keys.md) and [05](05-admin-user-management.md) no longer say tokens are never recorded.
